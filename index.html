In its simplest form — just repeat the same prompt.

Repetition actually works

Leviathan, Kalman & Matias (2025) — arxiv.org/abs/2512.14982

47 / 70 benchmark-model combinations where repetition won 0 losses
  • No increase in output length or latency
  • Repetition happens in the parallelizable prefill stage
  • RL-trained reasoning models already repeat the user's request internally
  • The loop mirrors what models naturally want to do

Structured repetition

Each iteration isn't blind — it's repetition with accumulated context.

Iteration 1: prompt + ticket Iteration 2: prompt + ticket + test results Iteration 3: prompt + ticket + test results + review findings Iteration 4: prompt + ticket + test results + review + fix feedback Each loop carries forward what came before.

Bounded by input

You can loop forever on a vague ticket and get nowhere.

Planning is the leverage point.

Act II

Planning is
Development

2
"Planning isn't a phase before development — it is development. Therefore all developers must become architects."

The architect shift

Before agents

Architect → plans solution Developer → writes code Reviewer → checks code Only architects plan.

With agents

Developer → plans solution Agent → writes code Developer → reviews code Everyone plans.

The shift: from "coding" to "planning and refining."

How Lisa plans

Before writing code, Lisa generates 5–20 granular steps.

Lisa plan output
Step 1: Create WebhookController
  Files: CREATE src/controllers/webhook.ts
  Template: src/controllers/notification.ts

Step 2: Add WebhookService with retry logic
  Files: CREATE src/services/webhook.ts
  Template: src/services/email.ts

Step 3: Add database migration
  Files: CREATE migrations/20250224_webhooks.sql

Assumptions:
  P.1 Using existing auth middleware (not new system)
  P.2 PostgreSQL for storage (not Redis)

The implication

If planning is development, the skill every developer needs is planning.

That's what architects do.

This isn't diminishing coding skill — it's elevating the role.
You need deep technical understanding to plan well for agents.

Act III

Building Blocks

Claude Code as a function

Not a chatbot — a building block.

Headless mode
# Call Claude, get output
$ claude --print "Explain this code"

# Pipe context in
$ cat src/auth.ts | claude -p "Security issues?"
Structured output
# Predictable JSON responses
$ claude -p \
--output-format json \
--json-schema '{...}' \
"Analyze this PR"

Autonomy with control

Terminal
# Full access (sandboxed environments only)
$ claude -p --dangerously-skip-permissions "Fix all lint errors"

# Precise control — whitelist tools
$ claude -p \
--allowed-tools "Read,Write,Bash(npm test)" \
"Fix the failing tests and verify"

Cost & speed optimization

Not every call needs the heavy model.

Model selection
# Heavy thinking
$ claude --model opus

# Daily work
$ claude --model sonnet

# Quick extraction
$ claude --model haiku --effort low
Lisa mixes models: Planning → Opus Implementation → Sonnet Extraction → Haiku + low effort Review → Sonnet Right model for the right task.

Act IV

Verification

3
"Agents can generate and analyze code, but verifying business correctness is still unsolved."

What agents are good at

Strong

  • Code quality & conventions
  • Test coverage gaps
  • Security patterns (OWASP)
  • Type errors & null safety
  • N+1 queries & performance

Weak

  • Business logic correctness
  • Domain model alignment
  • "Does the webhook fire at the right time?"
  • "Does the event name match the domain?"
  • Verifying the reviewer's judgment

Lisa's partial answers

Reviewer Guide
Review Guide: ENG-456

Purpose: Real-time webhook notifications
Entry: POST /api/webhooks → WebhookController
Flow:
  1. Request validated by schema
  2. WebhookService.create() persists
  3. Dispatcher queues async delivery

Key Review Points:
  ⚠ WebhookDispatcher.send()
    Async HTTP call with 5s timeout
  • Reviewer guide — purpose, flow, risk flags
  • Assumption tracking — every decision recorded (P.1, 1.1, 2.1...)
  • Linear comments — team visibility into progress
  • review-ticket skill — validate before implementation

Honesty

This is active exploration, not a solved problem.

Lisa is meant to explore solutions — not claim to have found them.
